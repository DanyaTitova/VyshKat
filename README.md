Проект консольного приложения для управления парком кикшеринга **«ВышКат»**, реализованный на C# с применением принципов **Clean Architecture**, **SOLID** и механизмов **Dependency Injection (DI)**.

# Архитектура и Структура Проекта

Проект структурирован с четким разделением зон ответственности:

```text
VyshKat/
├── src/
│   └── VyshKat.App/                 # Основное консольное приложение
│       ├── Abstractions/            # Интерфейсы сущностей (IInventory, IEnergyConsumer)
│       ├── Models/                  # Доменные модели (Vehicle, Scooter, Bike, EBike, Item)
│       ├── Services/                # Бизнес-логика (FleetManager, StandardServiceCenter)
│       ├── UI/                      # Пользовательский интерфейс и адаптеры ввода/вывода
│       ├── Program.cs               # Точка входа и сборка DI-контейнера
│       └── VyshKat.App.csproj       # Конфигурация проекта приложения
├── tests/
│   └── VyshKat.Tests/               # Юнит-тесты (xUnit + NSubstitute)
│       ├── FleetManagerTests.cs     # Тесты бизнес-логики управления флотом
│       ├── ConsoleMenuTests.cs      # Тесты пользовательского меню
│       └── VyshKat.Tests.csproj     # Конфигурация тестового проекта
└── VyshKat.sln                      # Файл решения (Solution)
```
1. Сборка решения
dotnet build
2. Запуск юнит-тестов
dotnet test
3. Запуск приложения
dotnet run --project src/VyshKat.App/VyshKat.App.csproj

# 1. Как в проекте соблюдаются принципы SOLID?
    Single Responsibility Principle: Каждый класс отвечает только за свою задачу. ConsoleMenu отвечает за отображение меню и ввод/вывод, FleetManager — за бизнес-логику управления парком, StandardServiceCenter — за проведение техосмотра, а модели (Scooter, Bike, Item) хранят только данные состояния.

    Open/Closed Principle: Система открыта для расширения, но закрыта для изменений. Для добавления нового типа транспорта достаточно унаследоваться от Vehicle, не меняя код FleetManager.

    Liskov Substitution Principle: Любой наследник Vehicle (Scooter, Bike, EBike) может быть передан в места, где ожидается базовый класс или интерфейсы IInventory / IEnergyConsumer, без нарушения работы программы.

    Interface Segregation Principle: Интерфейсы разделены по смыслу: IInventory отвечает за учет и инвентарный номер, IEnergyConsumer — за расчет энергопотребления. Классы имплементируют только те интерфейсы, которые им действительно нужны (например, Item реализует только IInventory).

    Dependency Inversion Principle: Модули верхнего уровня не зависят от модулей нижнего уровня. FleetManager и ConsoleMenu зависят от абстракций (IServiceCenter, IConsoleAdapter), а не от их конкретных реализаций.

# 2. Зачем используется Dependency Injection (DI) и IoC-контейнер?
    DI позволяет ослабить связность компонентов. В Program.cs настраивается ServiceCollection, который автоматически внедряет нужные зависимости через конструкторы. Это позволяет подменять реальные сервисы на мок-объекты при написании юнит-тестов без изменения самого кода приложения.

# 3. Как абстрагирован ввод-вывод консоли для изолированного тестирования?
    Создан интерфейс IConsoleAdapter с методами ReadLine(), Write() и WriteLine(). В реальном приложении используется SystemConsoleAdapter, а в юнит-тестах (ConsoleMenuTests) передается мок, симулирующий пользовательский ввод и позволяющий проверять текстовый вывод меню.

# Использование ИИ в работе:
Данный проект был разработан самостоятельно. Использование генеративных нейросетей и ИИ-инструментов было строго ограничено и сведено к минимуму. Где ИИ использовался:
Отладка и локализация ошибок сборки: ИИ привлекался исключительно для быстрой диагностики ошибок компиляции .NET CLI (таких как CS5001, CS0246), возникавших из-за расхождений в путях csproj, рассинхронизации версий SDK (.NET 8 vs .NET 10).
